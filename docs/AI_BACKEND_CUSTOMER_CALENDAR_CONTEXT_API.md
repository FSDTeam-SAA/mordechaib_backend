# AI Backend Customer and Calendar Context API

## Purpose

This is the service-to-service read contract for an AI Chief of Staff that
needs grounded customer and calendar facts. Main Backend remains the source of
truth and the only component allowed to mutate customers, tasks, meetings, CRM
records, or calendars.

The AI Backend may use these routes to:

- find a customer using business-facing fields;
- load one bounded customer workspace;
- inspect calendar events in an explicit period;
- obtain deterministic free-slot suggestions and scheduling conflicts.

These routes are not public frontend APIs. They return raw JSON without the
public `{ success, data }` envelope.

## Authentication and tenant scope

Every request must include:

```http
x-ai-actions-secret: <shared-service-secret>
```

Every request must also include `requesterUserId` as a query parameter. Main
Backend verifies that this user is active and belongs to the organization in
the path. A valid service secret does not bypass tenant/requester scope.

Never accept an organization or requester ID generated by the model. Use the
IDs supplied to the AI Backend by Main Backend for the current chat turn.

Authentication failures:

- `401`: missing or invalid shared secret;
- `404`: organization-scoped active requester does not exist;
- `400`: malformed organization, requester, range, filter, or pagination.

## 1. Search customers

```http
GET /api/v1/ai-internal/organizations/{organizationId}/customers
  ?requesterUserId={userId}
  &search={query}
  &status=ACTIVE
  &page=1
  &limit=20
```

Optional filters:

- `search`: case-insensitive match over name, email, phone, company, job title,
  location, and tags;
- `status`: `ACTIVE` or an available contact status;
- `leadStatus`: an available lead status;
- `page`: minimum `1`;
- `limit`: `1..100`.

Example:

```http
GET /api/v1/ai-internal/organizations/6a.../customers?requesterUserId=6b...&search=Acme&page=1&limit=10
x-ai-actions-secret: <secret>
```

Response shape:

```json
{
  "organizationId": "6a...",
  "requester": {
    "userId": "6b...",
    "name": "Business Owner",
    "role": "OWNER"
  },
  "items": [
    {
      "id": "6c...",
      "name": "Sarah Johnson",
      "email": "sarah@acme.com",
      "phone": "+14155550101",
      "company": "Acme Ltd.",
      "jobTitle": "Operations Director",
      "location": "New York, USA",
      "leadStatus": "QUALIFIED",
      "tags": ["enterprise"]
    }
  ],
  "pagination": {
    "page": 1,
    "limit": 10,
    "total": 1,
    "pages": 1
  }
}
```

Use this route first when the organizer refers to a customer by name, company,
email, or phone. If multiple records match, the AI should ask the organizer to
choose; it must not guess.

## 2. Get one customer context

```http
GET /api/v1/ai-internal/organizations/{organizationId}/customers/{customerId}
  ?requesterUserId={userId}
  &taskLimit=5
  &meetingLimit=5
  &callLimit=5
  &noteLimit=3
  &fileLimit=5
```

Every limit is bounded to `1..20`. The response contains the existing customer
workspace read model, including:

- customer profile;
- linked CRM summary and grounded commercial metrics;
- open tasks;
- upcoming meetings;
- recent explicitly linked calls;
- latest persisted customer health;
- recent notes and file metadata;
- availability markers for data that does not exist.

Response outline:

```json
{
  "organizationId": "6a...",
  "requester": {
    "userId": "6b...",
    "name": "Business Owner",
    "role": "OWNER"
  },
  "customer": {
    "contactId": "6c...",
    "asOf": "2026-11-13T06:00:00.000Z",
    "profile": {},
    "crm": {},
    "tasks": {},
    "meetings": {},
    "calls": {},
    "health": {},
    "notes": {},
    "files": {}
  }
}
```

Frontend execution capabilities and endpoint action contracts are deliberately
not exposed. The AI may use facts to prepare a proposal, but must never claim
that it sent an email, created a task, changed CRM, or scheduled a meeting.

## 3. List calendar events

```http
GET /api/v1/ai-internal/organizations/{organizationId}/calendar/events
  ?requesterUserId={userId}
  &from=2026-11-13T00:00:00.000Z
  &to=2026-11-20T00:00:00.000Z
  &page=1
  &limit=50
```

Optional filters are `provider`, `meetingType`, and `status`. `from` and `to`
are ISO-8601 timestamps. Pagination is mandatory and bounded to 100 rows per
page. AI must not download an organization's unbounded calendar history.

This route returns normalized platform-managed/synchronized event facts. Use
it for questions such as “What meetings do I have this week?”

## 4. Get calendar availability

```http
GET /api/v1/ai-internal/organizations/{organizationId}/calendar/availability
  ?requesterUserId={userId}
  &from=2026-11-13T00:00:00.000Z
  &to=2026-11-20T00:00:00.000Z
  &timezone=Asia%2FDhaka
  &suggestionDurationMinutes=30
  &bufferMinutes=15
  &suggestionLimit=5
  &conflictLimit=20
```

Rules:

- `from` and `to` are required and `from < to`;
- maximum range is 730 days;
- `timezone` must be an IANA timezone;
- duration is `15..240` minutes;
- suggestions are deterministic Main Backend results based on persisted busy
  events, organization business hours, timezone, duration, and buffer;
- the AI must not invent a slot outside the returned suggestions.

Response outline:

```json
{
  "organizationId": "6a...",
  "requester": {
    "userId": "6b...",
    "name": "Business Owner",
    "role": "OWNER"
  },
  "asOf": "2026-11-13T06:00:00.000Z",
  "timezone": "Asia/Dhaka",
  "range": {
    "from": "2026-11-13T00:00:00.000Z",
    "to": "2026-11-20T00:00:00.000Z"
  },
  "dataAvailability": {
    "availability": "AVAILABLE"
  },
  "calendarProvider": "GOOGLE",
  "busyEventCount": 4,
  "conflicts": {},
  "availability": {
    "availability": "AVAILABLE",
    "suggestions": []
  }
}
```

## Recommended AI flow

### Customer question

```text
receive current organizationId + requesterUserId
  -> search customers with a bounded query
  -> ask clarification when zero/multiple ambiguous matches exist
  -> fetch the selected customer context
  -> answer only from returned facts
```

### Meeting request

```text
identify customer/invitee
  -> search and resolve customer
  -> obtain explicit invitee email (ask if missing)
  -> request calendar availability for the requested range/timezone/duration
  -> prepare clarification or meeting proposal
  -> Main Backend validates and organizer approves
  -> Main Backend executes through the existing meeting/calendar adapter
```

## Grounding and privacy requirements

1. Never invent a customer, email, phone, task, deal value, health score,
   calendar event, or free slot.
2. `UNAVAILABLE` is not zero and must not be represented as zero.
3. Treat notes and customer data as tenant-private; do not log complete payloads.
4. Cache only for the current bounded turn when necessary; Main Backend remains
   the source of truth.
5. Do not expose this shared-secret API to browsers or mobile clients.
6. Do not use these GET routes to imply an external mutation occurred.
7. Use the dedicated chat proposal contract for task, meeting, and CRM actions.

## Required acceptance tests for AI Backend

- calls without the shared secret fail;
- organization/requester IDs always come from Main Backend context;
- customer search is paginated and ambiguous matches trigger clarification;
- customer detail limits are respected;
- calendar event calls always use an explicit bounded period;
- availability uses the organizer's effective IANA timezone;
- no slot outside `availability.suggestions` is proposed as confirmed;
- missing customer email triggers clarification;
- AI response says “ready for review,” never “created/scheduled,” before Main
  Backend execution;
- private customer/calendar payloads are absent from application logs.
